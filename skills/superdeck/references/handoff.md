# Handoff

Used to choose how to build (step 2.2, or the build line of the express proposal), to build (3.1) and to review the result (3.2).

## Choosing how to build

1. **Look at what this session can do right now** to produce slides: slide-deck artifact types, skills that build presentation files, connectors to apps that create presentations, and whether you can view the rendered result. Offer only what is actually available; never assume a tool exists, and don't present a capability you haven't seen described as certain. If the session can search for skills or connectors that aren't installed, you may mention one that would clearly help, in one line.
2. **Judge each option against this deck,** using what the gate documents already say: a mandatory template or brand identity; who edits the deck afterwards, and where; how it will be shared (a link, a file for the client, a PDF); the format and whether it needs speaker notes; what the visual concept demands (charts, custom layouts); and whether you can review the rendered slides, which the review in step 3.2 depends on. If the account has a design system and an option can apply it, say so.
3. **Present two to four viable options,** numbered, each with one pro and one con for this deck, and recommend one with the reason. In express mode, one line per option. Mention in one line the two fallbacks that always exist:
   - **Prompt for an external slide tool:** a complete, self-contained prompt built from the Production plan — context, audience, global rules and, slide by slide, title, visual, data and text. Warn that chart data must be checked afterwards, because external tools often alter it.
   - **Build checklist:** the Production plan formatted as a checklist, slide by slide, for the user to assemble by hand in the program they prefer.

If the chosen option needs a file (such as a template), ask for it before building. If it is no longer available when the build starts (for example, in a new conversation), say so and choose again.

## Building
- The Production plan is the specification, already decided with the user. Don't rewrite titles, add slides, swap visuals or invent data. If something isn't possible in the chosen tool, ask before adapting.
- Pass everything that was decided on to the build: global rules, identity, the content of each slide and the speaker notes.

## Review
Before delivering:
- **Against the Production plan:** every slide present, exact titles, correct data, highlight in the right place.
- **On the rendered deck** — images or a preview of the slides, not only the code or text: text cut off, overflowing or overlapping; a title longer than two lines; type too small for the format (live: legible from the back of the room); weak contrast; a chart highlighting the wrong figure or missing source and period; the same color meaning different things; a slide that breaks the visual concept.
- Fix what is only appearance; for anything that changes content, ask first.
- Tell the user what was fixed and what still diverges from the plan.

If the chosen tool doesn't let you see the result (a prompt for an external tool, a build checklist), deliver this review as a checklist for the user to run after assembling.

## After delivery
Adjustments requested after the build that change content (not just appearance) must also be recorded in the Script and the Production plan, so they remain the source of truth.
